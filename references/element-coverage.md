# 从原清单到实际模块

以用户的《神经网络模型构建要素清单》为完整性依据。Skill 内保留[原文副本](construction-elements-checklist.md)，包含十四类、86 条详细事项、通用与按需内容的区别，以及模块统一填写表。工作区原文可访问时先比较；有变化时更新副本和模板，不能悄悄删减条目。副本用于随 Skill 分发，不另立一套科学标准。

本页完整填写要求适用于完整网络方案、正式构建及相应交付。仅讨论、初步调研或用于选型的最小探索按[执行深度](workflow-checks.md#探索小运行与正式构建)保留必要记录，不先填一套尚未选定网络的空表。进入正式构建时落实全部事项；不能用“探索”免除最终任务中的必需要素。

## 一条事项对应到哪里

将[逐项表模板](../assets/element_coverage.csv)用于项目 `docs/element_coverage.csv`，保留全部详细事项。原编号在[固定目录](element-catalog.json)中成为永久 ID；不因原文插入或移动条目而重新编号。模板只有原文，没有预填“完成”。版本和更新方式见[联合检查说明](project-checks.md#清单更新与固定编号)。方案、实现和结果引用同一份表；局部修订只更新受影响条目，不能以十四个标题代替详细事项。

| 字段 | 填写规则 |
|---|---|
| `item_id, requirement` | 原文编号和完整事项，不删行、不改写要求。 |
| `handling` | `explicit` 显式计算或定义；`simplified` 简化；`fixed` 固定条件；`external` 外部输入；`not_applicable` 不适用。同一事项有多个子条件时在决定中分别交代，主处理方式取本轮实际采用方式。 |
| `decision` | 具体采用什么、适用对象及限制。写数值/方法说明的位置，不能只写“已考虑”。 |
| `module_ids` | 实际负责该事项的模块标识，以 `\|` 分隔；模块可以跨类别，一个事项也可对应多个模块。通用定义可引用说明，无须虚构计算模块。 |
| `spec_ref` | `docs/model_spec.md#位置` 等项目内构建方法引用。已有详细内容直接引用。 |
| `check_refs` | 已有的逐项核对或运行记录，以 `\|` 分隔；方案阶段可留空。检查记录写实际命令、使用的配置/版本、输出、判定及未完成项，同一报告可被多行引用。 |
| `status` | `planned` 尚未落实；`documented` 已明确的说明项；`implemented` 已写代码未查运行；`checked` 已实际核对；`not_applicable` 仅用于不适用事项。 |
| `reason` | 简化、固定、外部输入或不适用的理由、对目标输出的影响与适用范围；不能用“缺代码”解释不适用。 |

**通用定义均需明确；目标依赖的机制必须落实。** 把用户指定的模块以及由目标输出推导出的必要事项，连同理由填入模块表的 `required_items`。例如，研究空间传播时需要位置与空间连接；研究场信号时需要内部活动到场信号的计算；研究可塑性时需要状态、更新和边界。这些事项不能标为不适用。简化或外部输入仍须实现相应计算/读取与接口检查，并限定结论范围；如果简化会改变用户已定目标，先解决该科学选择，不能自行取消目标。

清单没有要求所有模型同时采用真实三维形态、多区室、HH、可塑性、血流和胶质过程。空间不参与计算时仍需明确该决定；未采用附加机制时仍需说明选择。群体模型的连接和耦合按群体变量定义，不能因为没有逐个突触就整类留空。只做单细胞任务时，网络连接可不适用；必须如实标明任务范围，不能将网络任务改标为单细胞来通过检查。

## 每个启用模块的七项定义

以[模块表模板](../assets/module_contracts.json)建立项目 `model/module_contracts.json`。这是一份实际模块索引，引用已有配置与方法，不复制另一套参数。`model_scope` 为 `network`、`population_network` 或 `single_cell`；`required_items` 是“事项编号: 必须具备的原因”的对象。`modules` 只登记实际计划启用的模块；实现后与当前代码一致。七项定义都填写具体内容或准确的章节引用：

| JSON 字段 | 原清单字段与内容 |
|---|---|
| `function_object` | 功能与对象：过程及其作用的群体、细胞或脑区。 |
| `inputs` | 输入：名称、单位、来源和作用对象。 |
| `equations_implementation` | 方程与实现：方程/算法、模型与版本、实现来源。 |
| `parameters` | 参数：对应表与配置位置、单位、分布、来源和允许范围。 |
| `states_initialization` | 状态与初值：全部状态、初值和更新归属；无状态算法明确写明，不凭空增加状态。 |
| `outputs_connections` | 输出与连接：名称、单位、接收模块和进入的方程或处理位置。 |
| `timing` | 时间设置：求解、更新、交换和记录间隔；一次性构建步骤明确执行时机。 |

模块索引记录 `catalog_version,plan_id,model_version,dynamics`。每个模块有唯一 `module_id`，`parameter_ids,step_ids` 关联参数与步骤；数组 `code_refs,result_refs,check_refs` 分别指向源码/后端定义、实际数据和[结构化检查记录](project-checks.md#记录实际检查不手工填写成功标签)，可带位置说明。`status` 为 `planned/implemented/checked`。方案阶段写计划源码，结果和检查可为空；实施阶段工具读取检查判定、指标及文件一致性，不能只填成功标签。多份检查可共同覆盖模块源码和输出。

按细胞与群体、空间、连接、突触或耦合、输入、初始化与求解、记录/观测、分析等实际职责组织模块，具体文件结构见[工程规则](project-layout.md)。一个模块可以有多个代码文件，多个事项可共用模块；不强行生成十四个文件，也不能把全部模型代码装进一个文件。参数、初始化与随机过程可由相关模块共同负责，必须写清各自职责。附加机制启用后也填写完整七项并进入主运行入口；空类、占位函数、没有接入计算的文件不算实现。

## 构建前、运行后分别检查

1. **完整方案与正式构建前**逐项填写处理方式和理由，依据研究目标登记必需事项；完成所有启用模块的七项定义与计划实现位置。核对模块间单位、输入输出、状态归属、时间设置及构建顺序。尚未解决的必需决定保持待完成，不能标成通过。只委托方案时到此结束，不生成运行结果。
2. **实施中**将这些定义落实到实际文件和主入口。检查生成的细胞/群体、适用时的坐标、连接/耦合与突触参数，核对初始化、刺激送达、状态演化、记录及分析。针对每个启用模块从实际数据检查输入是否到达、输出是否被使用、作用方向和单位是否正确；对关键机制增加适用的独立输入、关闭机制或变化参数比较。静态构建模块检查实际生成结构，无须假造时间轨迹。
3. **交付前**更新逐项表和模块索引，运行下面的完整性检查，再按[阶段检查](workflow-checks.md)审阅实际运行与数值结果。方法有写、代码存在、检查通过和实测支持是不同状态。必需模块缺失或仍未核对时，报告未完成项，不宣称完整模型已交付。

```text
python <skill_dir>/scripts/check_elements.py --project <project> --phase plan
python <skill_dir>/scripts/check_elements.py --project <project> --phase implemented --output results/<run_id>/element_check.json
```

默认读取项目的 `docs/element_coverage.csv` 和 `model/module_contracts.json`。位置不同可用 `--coverage`、`--modules` 指定。项目外的原始清单可用 `--source-checklist` 指定，与 Skill 副本比较；没有原文件时报告只依据随附副本。`--checklist` 可指定随交付保存的清单。独立工程若使用此工具，将脚本及清单一起保存到 `tests/` 等适当目录，并用该参数引用，不能依赖个人 Skill 路径。

工具检查事项与固定目录、必需项、模块七项定义，以及实施检查的判定、实际指标和代码/配置/数据是否改变。任务要求与参数、步骤、结果的对应还须执行[联合检查](project-checks.md)。科学适用性、函数是否接入、运行记录是否真实仍需实际阅读和运行核对。工具不证明生物学正确；参数、网络及实际实例数值另用[数值工具](automatic-checks.md)。

工具默认只读并输出 JSON。`--output` 只允许在项目内已有目录中新建文件，不覆盖已有记录。报告中的通过只针对所列结构检查；计划检查通过不等于已经实现。原文变化后需先更新引用和编号，不能用旧表强行通过。
